1. Executive Summary & Problem Scope

The Academic Study Resource & Lending Management System is a functional C# application engineered to assist students, curriculum planners, and academic librarians in managing study materials, planning targeted learning schedules, and enforcing safe book reservations.

In educational environments, students often face information overload with unstructured literature, while academic libraries struggle with inconsistent loan rules, temporal sequencing bugs (such as approving loans before checking student quotas), and unhandled runtime exceptions. This application addresses these challenges by building a mathematically sound Functional Core:

  • Structured Domain Data: Immutable core models representing books, study modules, curriculum plans, and loan state machines.
  • Three Distinct Meaningful Workflows: Combining input validation, business rule execution, and deterministic results without mutable global state.
  • Two In-Depth Analytical LINQ Reports: Aggregating author reach, productivity, native priority scores, and historical decade trends.
  • Safe Operation Sequences: Eliminating temporal coupling via typed state transitions and factories.
  • Explicit Outcomes: Total elimination of nulls using Option<T> and Result<T, DomainError> with real Map and Bind composition.

2. Coherent Domain Models

The application includes three interconnected, fully immutable domain models implemented as C# sealed record types with ImmutableArray<T> collections:

Model Type C# Representation Domain Purpose Immutability Guarantee
Book sealed record Book(...) Core resource entity containing title, authors, first publish year, edition count, OpenLibrary key, and languages. Positional record with ImmutableArray<string> collections. Defensively copied upon parsing.
StudyPlan sealed record StudyPlan(...) Curriculum plan composed of ordered StudyModule records, assigned weekly reading hours, and difficulty objectives. Immutable sequence of weekly modules; workload metrics computed at creation.
LoanState abstract record LoanState Closed algebraic state hierarchy (Draft, Validated, Approved, Rejected) modeling student book lending. Enforces compile-time and runtime validation; prevents illegal transitions or duplicate approvals.

3. Meaningful Workflows Walkthrough

Workflow 1: Resource Discovery & Policy-Based Scoring

Inputs: Live OpenLibrary API query or local JSON dataset, minimum publication year threshold, and a scoring policy delegate.
Business Rules: Year threshold filtering, higher-order scoring calculation (Popularity vs Recency vs Curried weights), and deterministic ranking with ordinal title tie-breaking.
Pipeline: FilterBooksResult -> ScoreBooksResult -> RankBooks composed via Bind and Map.
Result: Immutable list of ranked Recommendation items.

Workflow 2: Personalized Study Plan Generation

Inputs: Subject/topic string, student difficulty level (Beginner, Intermediate, Advanced), target weeks (1..52), and maximum books per author.
Business Rules:

  1. Stage 1 (Filter): Rejects materials published before the difficulty's era threshold (Beginner: 1990, Intermediate: 2005, Advanced: 2015).
  2. Stage 2 (Higher-Order Diversity Constraint): Enforces author diversity using a custom predicate so no single author dominates the syllabus.
  3. Stage 3 (Pattern-Matching Scheduling): Employs pattern matching to assign weekly study hours (Beginner: 4h, Intermediate: 8h, Advanced: 12h) and tailored learning objectives.
Result: Immutable StudyPlan detailing weekly modules and total workload.

5. Architectural Boundaries: Pure Functional Core vs Side Effects

The application enforces strict architectural boundaries to preserve functional purity:

  • Boundary Layer (I/O & Side Effects): Handles file access (OpenLibraryClient.LoadFromFileResult, ReportExporter.ExportReportAsync), network HTTP requests (OpenLibrary API), and user console prompts (Program.cs). Operational exceptions are intercepted immediately at the boundary and converted to immutable DomainError values.
  • Pure Domain Core: All validation (BookParser, ValidatedSearch), workflows (BookPipeline, StudyPlanWorkflow, LoanWorkflow), scoring policies (CurriedScoring), and report queries (LinqReports) are pure mathematical functions. They have no references to Console, file system handles, clock APIs, or mutable global state.

7. Project Limitations (Ограничения проекта)

The project operates within well-defined, intentional constraints aligned with its functional academic scope:

  1. Open Library API Pagination & Rate Limits: The live API client is configured with a deterministic ceiling of 10 search results (limit=10) per query. While adequate for targeted course research, broad search queries return a single page of results without interactive cursor pagination.
  2. In-Memory Session Persistence: Catalog updates and issued loans are maintained within the running session and exported to disk as formatted text and report artifacts (reports/*.txt). The system deliberately avoids an external relational database (e.g. PostgreSQL) to preserve zero-dependency functional purity.
  3. Defensive Handling of Optional Metadata: In the Open Library JSON schema, author names and language lists are frequently omitted. Rather than rejecting viable books, the parser treats missing collections as empty arrays (ImmutableArray<string>.Empty), causing them to display as "unknown" in author aggregations.
  4. Platform Architecture for Native Routines: The low-level hardware acceleration assembly routine is compiled specifically for x86-64 (AMD64) architectures (ELF64 System V ABI on Linux and Microsoft x64 calling convention on Windows). Running on non-x86 architectures (such as ARM64 Apple Silicon) requires recompilation with an ARM-compatible toolchain.

Defects Discovered and Resolved During Testing

Writing automated tests prior to final integration exposed three notable defects that were systematically resolved:

  1. Temporal Coupling in Book Loan Approvals:
    Defect: Early prototypes allowed calling approval logic directly on unvalidated requests, permitting borrowers to bypass tier quotas and catalog checks.
    Resolution: Refactored the workflow into a closed algebraic data hierarchy (LoanState.Draft -> Validated -> Approved). Transition methods reject invalid state sequences at runtime with Result.Failure("InvalidStateTransition").
  2. Dynamic Shared Object Resolution under VSTest Runner:
    Defect: During dotnet test execution, the VSTest runner runs in a working directory different from the test assembly bin directory, causing DllNotFoundException for libcalc.so.
    Resolution: Implemented a custom NativeLibrary.SetDllImportResolver in NativeBridge.cs that resolves libraries explicitly relative to AppContext.BaseDirectory.
  3. Stream Descriptor Leak on Early Iterator Termination:
    Defect: Calling Take(1) on StreamLines left file descriptors open on Linux, causing subsequent file deletion tests to throw IOException.
    Resolution: Enclosed the FileStream and StreamReader in a C# using block inside the iterator method, ensuring the enumerator's Dispose() immediately closes file handles upon early exit.
